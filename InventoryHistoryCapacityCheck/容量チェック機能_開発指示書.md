# 【指示書】Supabase DB容量監視・閾値超過時メール通知機能

作成日: 2026-07-13
対象: Antigravity（実装担当）
レビュー: Claude（実装後レビュー）
関連Issue: #32（本体）／#28（退避機能・関連）
プロジェクトフォルダ名: `InventoryHistoryCapacityCheck`
ブランチ名: `feature/inventory-history-capacity-alert_20260713`

---

## 1. 背景と目的

`ne_inventory_history` テーブルについて、Issue #28にて「直近15ヶ月保持・16ヶ月超で外部退避」という時間ベースの保持ルールを決定した。これは現状の成長率（実測値ベース）を前提とした試算であり、将来的にSKU数やイベント頻度が増加すると、想定より早く容量が膨らむ可能性がある。

退避機能（Issue #28）の実装に先行し、DB容量を定期的に監視し、想定外の超過を早期検知できる仕組みを本プロジェクトで構築する。

---

## 2. スコープ

**本プロジェクトに含む**
- GASによる定期的な容量チェック
- 閾値（80MB／90MB／100MB）超過時のメール通知

**本プロジェクトに含まない（別途対応）**
- Supabase側のRPC関数の作成（Claudeが先行してSupabase MCP経由で作成・検証済みのものを利用する。契約は本書 4章を参照）
- データ退避処理そのもの（Issue #28で別途対応）

---

## 3. 新規プロジェクト構成

既存の `GetInventoryData` / `DistributeInventory` / `InventoryChangesExport` と同様に、独立したGASプロジェクトとして新規作成する。

### ファイル構成（命名規則: `NN_英語名.日本語説明.gs`）

```
00_Config.設定値.gs
01_CapacityChecker.容量取得とRPC呼び出し.gs
02_Notifier.閾値判定とメール通知.gs
03_Trigger.日付判定（防御的チェック）.gs
99_Utils.ログユーティリティ.gs
README.md
```

`99_Utils` には、既存プロジェクトの `logError` / `logWithLevel`（JST表示・UTC保持の方針）と同等の関数を移植する。`InventoryChangesExport` と同様にスタンドアロン運用のため、共有ライブラリ化はせずファイルをコピーする。

## 4. Supabase側の前提（契約）

以下のRPCがSupabase側に既に作成されている前提で実装すること。**この関数自体の作成はAntigravityの作業範囲外。**

```sql
-- RPC名: get_table_size_mb
-- 引数: target_table (text) - 対象テーブル名
-- 戻り値: numeric - テーブルサイズ（MB、小数点2桁程度）
```

呼び出しイメージ（既存プロジェクトのRPC呼び出しパターンを踏襲）:

```
POST {SUPABASE_URL}/rest/v1/rpc/get_table_size_mb
Body: { "target_table": "ne_inventory_history" }
Headers: apikey, Authorization（既存プロジェクトと同じ anon key 運用）
```

Supabase接続情報（URL・anon key）は既存プロジェクトと同様に `PropertiesService` で管理する想定。既存プロジェクトのスクリプトプロパティを流用するか、本プロジェクト用に新規登録するかは実装時に確認すること。

## 5. 機能仕様

### 5.1 チェック対象・閾値

- 対象テーブル: `ne_inventory_history`
- 閾値: 80MB / 90MB / 100MB の3段階
- 現在サイズが閾値以上の場合、該当する閾値ごとにメール通知（例: 92MBなら80MB・90MBの2件を通知、既に通知済みかどうかの重複排除は行わない。5.4節「今後の課題」を参照）

### 5.2 実行タイミング

- **トリガーの登録はコードで自動化せず、GASエディタのトリガー管理UIから手動で行う**運用とする
- 毎月「1日・11日・21日・31日」の早朝に実行されるよう、**月次（特定日）トリガーを4つ個別に登録**する（時刻は既存の固定トリガー安全網の実行時刻を参考に、他の処理と重複しない時間帯を選定）
- **注意点**: GASの月次トリガーは、対象の日が存在しない月（31日トリガーの場合、2・4・6・9・11月）はその月は発火しない仕様。今回は運用上許容し、README.mdに明記する
- 関数内には、当日の日付（JST基準）が「1の位が1の日」であるかを確認する**防御的チェックロジック**を残す。これはトリガーの誤設定や手動実行時の誤爆を防ぐための保険であり、スケジューリングの主目的はコード側では持たせない（対象日でなければ早期リターンしてログのみ残す）

### 5.3 通知内容

通知先: GASプロジェクト作成アカウントのメールアドレス（`Session.getActiveUser().getEmail()` で取得、固定値のハードコードは避ける）

メール本文に含める項目:
- チェック日時（JST表示）
- 対象テーブル名
- 現在の容量（MB）
- 超過した閾値
- （参考情報として）無料枠500MBに対する割合

### 5.4 今後の課題（本プロジェクトのスコープ外・別Issueで検討）

- 同一閾値への重複通知の抑制（例: 一度通知したら次に閾値を跨ぐまで再送しない）
- Slack等、メール以外の通知チャネルへの拡張
- 複数テーブルへの監視対象拡大

## 6. 実装ステップ（スモールステップ）

1. **00_Config.gs**: 閾値配列・対象テーブル名などの定数定義
2. **99_Utils.gs**: 既存プロジェクトから `logError` / `logWithLevel` を移植
3. **01_CapacityChecker.gs**: RPC呼び出し→容量取得（手動実行で動作確認、ログ出力のみでこの時点では通知しない）
4. **02_Notifier.gs**: 閾値判定ロジック→メール送信（手動実行で、閾値を一時的に下げるなどしてテスト送信を確認）
5. **03_Trigger.gs**: 「1の位が1の日」かどうかを判定する防御的チェック関数のみを実装する。**トリガー自体はコードで自動登録しない**（GASエディタから手動で月次トリガーを4つ登録する運用）
6. **README.md**: プロジェクト概要、各ファイルの役割、閾値の意味、**トリガーの手動登録手順**（対象4日・時刻・31日トリガーの注意点を含む）を記載

各ステップごとにClaudeへ報告し、次のステップに進む前に動作確認結果を共有すること。

## 7. コーディング規約（既存プロジェクト共通）

- 全関数に JSDoc（`@file` ヘッダー含む）を必須とする
- `try-catch-finally` ＋ `logError`/`logWithLevel` パターンを踏襲
- ログの日時表示はJST変換、Supabase APIへのリクエスト値はUTCのまま保持
- 既存コードを修正する場合、説明文（コメント）は可能な限り残すか、内容に応じて修正すること（該当なし、本プロジェクトは新規作成のみ）
- **使用方法（トリガーの手動登録手順を含む）は README.md に記載する**。加えて、各ファイルの `@file` ヘッダーにもそのファイルの役割と使い方を簡潔に記載する
