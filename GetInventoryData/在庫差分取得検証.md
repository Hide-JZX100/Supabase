# 引継ぎ資料：在庫最終更新日フィールド検証 → 差分取得設計

**作成日**: 2026-08-16
**元スレッド**: GetInventoryData（Google Sheets向け）での`stock_last_modified_date`調査
**引継ぎ先**: Supabaseを使った在庫情報取得＆配布プロジェクト（別リポジトリ・別スレッド）

---

## 1. 背景・目的

Next Engine在庫マスタAPIのフィールド一覧に以下2つの日時フィールドがあることを発見し、中身を検証した。

| フィールド名 | 説明 |
|---|---|
| `stock_last_modified_date` | 最終更新日 |
| `stock_last_modified_null_safe_date` | 最終更新日（NULLの場合は作成日を返す） |

目的は、このフィールドを使って「前回取得以降に更新された商品だけ」を取得する**差分取得（インクリメンタルシンク）**が可能かどうかを検証すること。差分取得が実現できれば、API呼び出し回数・処理時間を大幅に削減できる可能性がある。

---

## 2. 確認済みの事実

### 2-1. `stock_last_modified_date-gte` 演算子は正常に機能する（検証済み）

以下のテストで確認：

- `stock_last_modified_date-gte` に **2000-01-01 00:00:00**（十分に古い日時）を指定 → **5件ヒット**
- `stock_last_modified_date-gte` に **2099-01-01 00:00:00**（未来の日時）を指定 → **0件ヒット**

→ 演算子は無視されておらず、実際に絞り込みが機能していることを確認済み。
→ 日時フォーマットは `YYYY-MM-dd HH:mm:ss` で受理された。

### 2-2. 最終更新日を動かす要因は完全には特定できていない（未確定）

在庫数フィールド自体が変わっていなくても、**フリー在庫数（`stock_free_quantity`、在庫数−引当数などから算出される派生フィールド）の変動だけで`stock_last_modified_date`が更新される**ように見える、という観察がユーザーからあった。

- フリー在庫数は算出フィールドである以上、引当数などの変動で連動して変わるのは自然な挙動。
- ただし「具体的にどのフィールドの変化がトリガーになっているか」を厳密に切り分ける検証はまだ行っていない。
- **差分取得の実装自体には支障がない**（「最終更新日が動いた商品を拾う」という目的には、要因の特定は必須ではないため）。
- 気になる場合は、フリー在庫数だけを意図的に変動させて再検証する、という追加検証が可能。

## 3. 検証に使用したテストコード（参考・GAS版）

Google Apps Script環境（`GetInventoryData`プロジェクト内、`getStoredTokens()` / `NE_API_URL` / `updateStoredTokens()`が既に定義されている前提）で動作確認済み。Supabase側実装の参考として掲載。

```javascript
/**
 * stock_last_modified_date-gte フィルタが実際に機能しているかを検証するテスト関数。
 * 過去日時（全件ヒット想定）と未来日時（0件想定）で結果を比較する。
 */
function testStockLastModifiedGteFilter() {
    const oldDate = '2000-01-01 00:00:00';
    const futureDate = '2099-01-01 00:00:00';

    const resultOld = queryStockByLastModifiedGte(oldDate);
    const resultFuture = queryStockByLastModifiedGte(futureDate);

    Logger.log(`過去日時(${oldDate})でのヒット件数: ${resultOld.length}`);
    Logger.log(`未来日時(${futureDate})でのヒット件数: ${resultFuture.length}`);
}

/**
 * stock_last_modified_date-gte を指定して在庫マスタAPIを検索する。
 * @param {string} thresholdDateTime - 検索基準日時（例: '2000-01-01 00:00:00'）
 * @return {Array} 取得した在庫データの配列
 */
function queryStockByLastModifiedGte(thresholdDateTime) {
    const tokens = getStoredTokens();
    const url = `${NE_API_URL}/api_v1_master_stock/search`;

    const payload = {
        'access_token': tokens.accessToken,
        'refresh_token': tokens.refreshToken,
        'stock_last_modified_date-gte': thresholdDateTime,
        'fields': 'stock_goods_id,stock_last_modified_date,' +
                  'stock_last_modified_null_safe_date',
        'limit': '5'
    };

    const options = {
        'method': 'POST',
        'headers': { 'Content-Type': 'application/x-www-form-urlencoded' },
        'payload': Object.keys(payload).map(key =>
            encodeURIComponent(key) + '=' + encodeURIComponent(payload[key])
        ).join('&')
    };

    const response = UrlFetchApp.fetch(url, options);
    const responseData = JSON.parse(response.getContentText());

    if (responseData.access_token && responseData.refresh_token) {
        updateStoredTokens(responseData.access_token, responseData.refresh_token);
    }

    return (responseData.result === 'success' && responseData.data) ? responseData.data : [];
}
```

**注記（GetInventoryDataの既存規約）**：
- `getStoredTokens()`：`11_Config.設定管理.gs`内、Script Propertiesの`ACCESS_TOKEN`/`REFRESH_TOKEN`を読み込む
- `updateStoredTokens()`：`13_NextEngineAPI.API通信.gs`内、レスポンスのトークンに差分がある場合のみ保存（クォータ節約）
- ペイロードは`Object.keys().map().join('&')`で手動エンコードし、`Content-Type: application/x-www-form-urlencoded`を明示

Supabase側（Node.js/Edge Functions等）でも、認証・トークンローテーションの考え方（下記4章）は共通で踏襲する想定。

## 4. 差分取得の設計方針（合意済み部分）

### 4-1. チェックポイント記録タイミング

**「取得完了時刻」ではなく「取得開始前の時刻」を次回チェックポイントとして保存する。**

理由：取得処理の実行中（数秒〜数十秒）に商品が更新された場合、完了時刻を基準にすると更新分が抜け落ちる可能性がある。開始前時刻を基準にすれば、多少の重複取得（`-gte`は「以上」なので境界値がダブる）は起きるが、抜け漏れは防げる。

処理フロー：
1. API呼び出し**前**に現在時刻を`fetchStartTime`として保持
2. 保存済みの前回チェックポイントで`stock_last_modified_date-gte`検索を実行
3. 取得が**成功したら**、`fetchStartTime`を次回チェックポイントとして保存

### 4-2. チェックポイントの保存場所

**Script Properties**（GASの場合）に保存する方針で合意済み。Supabaseプロジェクトでは、DBのテーブル（設定用テーブル、または専用のsync_stateテーブル等）に置き換わる想定。キー名は既存の`ACCESS_TOKEN`/`REFRESH_TOKEN`命名規約に倣い、`STOCK_LAST_SYNC_DATETIME`のような名前を想定していた（Supabase側では適宜テーブル設計に合わせて再検討）。

### 4-3. 未決定事項（要判断）

**「初回実行」（チェックポイント未保存）のときの動作** — 3案を提示したが、まだ回答をもらっていない。

| 案 | 内容 |
|---|---|
| A | 全件取得（従来通り）にフォールバック |
| B | 十分に古い日時（例:2000年）を仮のチェックポイントとして扱う |
| C | エラーにして手動でチェックポイントを設定させる |

→ Supabaseプロジェクト側でも同じ論点が発生するため、新スレッドで改めて方針を決める必要あり。

## 5. Next Engine API 関連の既存知見（Claudeの記憶ベース・再掲）

Supabaseプロジェクトでも共通して必要になる可能性が高い知見：

- **トークンローテーション**：アクセストークン・リフレッシュトークンは毎APIコールで両方送信し、レスポンスのトークンペアを必ず保存する（片方のみ送信は過去バグの原因）。
- **エラーコード002002**（`access_token が不正です`）：API経由では回復不能。ブラウザ再認証（`generateAuthUrl()`）が唯一の回復手段。自動化不可。
- **ページネーション終了条件**：APIの`count`フィールド（常に上限値を返す）ではなく、返却レコード数が上限未満かどうかで判定する。
- **在庫マスタAPI**：`stock_goods_id-eq`（または`-in`）が正しい検索パラメータ。`fields`は必須パラメータ。フィールド名は`stock_`プレフィックス。
- **受注キャンセル区分**：type 0（有効）、type 3（他伝票に統合）は意図的に含める。他は除外（在庫プロジェクトでは直接関係ないが、他APIとの整合性のため記載）。
